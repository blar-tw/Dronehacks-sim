Microservices & Dialects

Seventeen years of backwards compatibility

Dialects are XML message set extensions layered on top of the core messages.
A dialect includes common.xml and adds its own messages in an allocated ID range. No core message is touched, dialects never collide.
Systems that don't speak a dialect ignore its messages and keep interoperating on the core set.
Proven for over a decade: ArduPilot runs its own dialect (ardupilotmega.xml), vendors ship dialects for gimbals, ADS-B, and companion devices.
Every improvement to the core is inherited automatically. Forks diverge. Dialects ride along.

Control Allocation (mixing)
Control allocation in PX4 maps desired forces and torques from the controller into actuator outputs like motors or servos. It abstracts the vehicle geometry, so the same control logic works for multirotors, planes, or hybrids by handling the mixing and actuator mapping behind the scenes.


Running realtime inside the Embedded Controller.
Position: When the sticks are released the vehicle will remain locked to a position in 3D space.
Altitude: When the sticks are released the vehicle will maintain current altitude.
Hold: Vehicle stops and hovers at its current GPS position.
Takeoff: Vehicle takes off to a specified height and waits further input.
Land: Lands vehicle at the position where the mode was engaged.
Mission: Starts a mission that was preloaded to the drone

External Flight Modes
External Flight Modes are Flight Modes that can be developed and executed from outside the Flight Controller and in a non-real time system.
When do External Flight Modes matter?
When you don’t need low-level access for direct motor control
When you have a compute module where you can run ROS 2
When the mode is not Safety Critical
Advantages
You don’t need to deal with low level embedded constraints and requirements
Crashing the app won’t result in a catastrophic failure
Easier to maintain outside of the PX4 codebase
Take advantage of high-level functionality like dynamic data structures, and the ROS 2 library ecosystem.
More advanced compute for greater processing

Custom Modes: Mode vs Mode Executor
Mode (px4_ros2::ModeBase)
Defines how the vehicle behaves during a custom flight mode.
Inherits from px4_ros2::ModeBase
Implements:
onActivate() / onDeactivate()
updateSetpoint() → generates control setpoints
Uses PX4 objects (e.g. ManualControlInput, RatesSetpointType)
Registered with mode->doRegister()
Focus: control logic, what the drone does right now
Think of this as the “brain” for a single flight mode.

Mode Executor (px4_ros2::ModeExecutorBase)
Coordinates multiple modes or actions into a higher-level behavior.
Inherits from px4_ros2::ModeExecutorBase
Owns one Mode (MyMode)
Defines states → e.g. TakingOff → MyMode → RTL
Uses helper actions: takeoff(), scheduleMode(), rtl()
Registered via executor->doRegister()
Focus: mission flow, when and in what order things happen
Think of this as the “mission director” controlling the brains.

Custom Modes: Mode vs Mode Executor
Mode (px4_ros2::ModeBase)
Defines how the vehicle behaves during a custom flight mode.
Inherits from px4_ros2::ModeBase
Implements:
onActivate() / onDeactivate()
updateSetpoint() → generates control setpoints
Uses PX4 objects (e.g. ManualControlInput, RatesSetpointType)
Registered with mode->doRegister()
Focus: control logic, what the drone does right now
Think of this as the “brain” for a single flight mode.

Mode Executor (px4_ros2::ModeExecutorBase)
Coordinates multiple modes or actions into a higher-level behavior.
Inherits from px4_ros2::ModeExecutorBase
Owns one Mode (MyMode)
Defines states → e.g. TakingOff → MyMode → RTL
Uses helper actions: takeoff(), scheduleMode(), rtl()
Registered via executor->doRegister()
Focus: mission flow, when and in what order things happen
Think of this as the “mission director” controlling the brains.

Aruco Marker detection
What is an ArUco Marker?
A binary square fiducial marker used for camera pose estimation.
Encodes a unique ID that can be easily detected in images.
Used to determine position and orientation of objects relative to a camera.
Why Use ArUco Markers
Fast and lightweight — works in real time on CPUs.
Highly reliable under varied lighting and partial occlusion.
No training data required, unlike AI-based object detection.
Deterministic performance — consistent and easy to debug.


Why OpenCV (vs. AI)
Open-source and widely supported in ROS and C++.
Low computational cost — ideal for embedded and robotics systems.
Easy integration with camera calibration and PnP solvers.
Predictable results without needing neural network inference.
3D Coordinate Frame Visualization
The 3D axes (X, Y, Z) show the marker’s orientation in space.
Allows intuitive visualization of camera–marker geometry.
Essential for pose estimation, control, and navigation tasks.
Helps debug spatial alignment in simulation and real-world setups.

Precision Land - Mode
The drone must convert target measurements from the camera’s frame (optical) to the drone’s local NED (North-East-Down) frame.
Transform Steps in Code:
Convert Aruco tag pose from optical frame to NED frame using a rotation matrix.
Transform tag position relative to the drone body frame.
Transform to world frame by combining drone position & orientation (affine transform).
Precision landing is the process of autonomously guiding a drone to land at a specific target (e.g., a marker or pad) with high accuracy, using onboard sensors (like cameras or LiDAR) to detect and track the target.
Key Features in this Implementation:
Uses Aruco markers as landing targets.
Performs spiral search pattern if the target is not immediately visible.
Maintains approach altitude, then descends once target is acquired.
XY motion uses a velocity controller with proportional–integral (PI) gains.
Uses land detection feedback to confirm landing success.
